Error responses

v2 uses RFC 9457 problem details with content type application/problem+json. The frozen /api/ v1 surface keeps its legacy JSON shape and returns Deprecation: true + Sunset headers.

Response shape (v2)

HTTP/1.1 400 Bad Request
Content-Type: application/problem+json

{
  "type": "https://api.google-play-api.dev/problems/bad-request",
  "title": "Bad Request",
  "status": 400,
  "detail": "num must be between 1 and 100",
  "code": "VALIDATION_ERROR",
  "instance": "/v2/apps/?num=0"
}

Fields:

  • type — stable URI identifying the problem class.
  • title — short human-readable summary, matches the HTTP reason phrase.
  • status — mirrors the HTTP status code.
  • detail — endpoint-specific explanation.
  • code — machine-readable code (e.g. VALIDATION_ERROR).
  • instance — the path of the offending request.

Unknown query parameters (v2)

On /v2/, query parameters the endpoint does not declare return 400 VALIDATION_ERROR instead of being silently forwarded upstream — string query values cannot satisfy upstream schema types like booleans (paginate on /apps/:appId/reviews was the motivating case, #192). The frozen /api/ v1 surface stays lenient and ignores unknown parameters for backwards compatibility.

Scraper-internal flags such as paginate are not exposed over HTTP. For deep review pulls, use the nextPaginationToken cursor on /v2/apps/:appId/reviews or the streaming /v2/apps/:appId/reviews/export endpoint (NDJSON/CSV).

Legacy v1 shape

HTTP/1.1 400 Bad Request
Deprecation: true
Sunset: Wed, 01 Jan 2026 00:00:00 GMT

{
  "error": {
    "message": "Invalid country code"
  }
}

Same paths, legacy body. Clients should migrate to the v2 shape — the v1 headers make the timeline explicit.
