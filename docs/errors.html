Error responses

v2 uses RFC 9457 problem details with content type application/problem+json.

StatusCodeMeaning
400VALIDATION_ERRORThe request parameters are invalid.
404HTTP_404The app or requested resource was not found.
429HTTP_429The request exceeded the configured rate limit.
502HTTP_502The upstream Play Store response could not be parsed.
503HTTP_503The upstream Play Store could not be reached.
500HTTP_500An unexpected server error occurred.

Response shape

{
  "type": "https://api.google-play-api.dev/problems/bad-request",
  "title": "Bad Request",
  "status": 400,
  "detail": "num must be between 1 and 100",
  "code": "VALIDATION_ERROR",
  "instance": "/v2/apps/?num=0"
}

Unknown query parameters

On /v2/, passing a query parameter the endpoint does not declare returns 400 with a problem document naming the offending parameter(s). Scraper-internal flags such as paginate are not exposed over HTTP; use the nextPaginationToken cursor on /v2/apps/:appId/reviews or the streaming /v2/apps/:appId/reviews/export endpoint for deep review pulls. The deprecated /api/ surface keeps its lenient posture (unknown parameters are ignored) until sunset.

Frozen v1 responses retain their legacy JSON shape and receive Deprecation: true and Sunset headers.

Unknown query parameters

On /v2/, query parameters that an endpoint does not declare are rejected with 400 VALIDATION_ERROR instead of being silently forwarded upstream — string query values cannot satisfy upstream schema types like booleans (paginate on /apps/:appId/reviews was the motivating case, issue #192). The frozen /api/ v1 surface stays lenient and ignores unknown parameters for backwards compatibility.
