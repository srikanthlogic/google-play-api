Throttling & Rate Limits

Rate limiting is implemented with express-rate-limit, scoped to /api/ routes. All settings are environment-configurable; there is no hardcoded limit.

v2 verification instance (gplayapiv2): throttling is disabled (RATE_LIMIT_DISABLED=true) so endpoint behavior can be verified without 429s. Enable it for any production use.

Environment settings

VariableDefaultDescription
RATE_LIMIT_DISABLED false Set true to disable rate limiting entirely. Used by the gplayapiv2 verification deployment.
RATE_LIMIT_WINDOW_MS 900000 (15 min) Length of the rate-limit window in milliseconds.
RATE_LIMIT_MAX_REQUESTS 100 Maximum requests allowed per window per IP.
RATE_LIMIT_SKIP_SUCCESSFUL_REQUESTS false Only count requests that returned errors.
RATE_LIMIT_SKIP_FAILED_REQUESTS false Only count requests that succeeded (2xx).

429 response

When the limit is hit, the API responds with 429 Too Many Requests, a Retry-After header, and a JSON body:

HTTP/1.1 429 Too Many Requests
Retry-After: 37

{
  "error": {
    "message": "Too many requests from this IP (100 requests per 15 minutes). Please try again after 37 seconds."
  }
}

Upstream timeout budget

Every upstream scraper call runs under a timeout budget so a slow Google Play response cannot hold a worker hostage. When the budget is exceeded the API responds with 504 Gateway Timeout and a Retry-After header.

VariableDefaultDescription
UPSTREAM_TIMEOUT_MS 15000 (15 s) Per-call timeout budget for every upstream scraper call.
UPSTREAM_TIMEOUT_RETRY_AFTER 5 Seconds advertised in the Retry-After header on 504 responses. 
HTTP/1.1 504 Gateway Timeout
Retry-After: 5
Content-Type: application/problem+json

{
  "type": "https://api.google-play-api.dev/problems/upstream-timeout",
  "title": "Gateway Timeout",
  "status": 504,
  "detail": "The upstream service did not respond within the timeout budget"
}

Operational notes

  • Limits are per-IP. Behind the Fly.io proxy the app trusts the proxy (trust proxy), so the client IP is used.
  • The limit is global to the instance, not per-endpoint or per-key. Per-key quotas are planned for the v2 SaaS tier (M3).
  • Disabling the limit (RATE_LIMIT_DISABLED=true) is only for verification deployments — production instances should always enable throttling to protect the upstream scraper from blocks.
